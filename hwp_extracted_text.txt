1.1 과제 개요
본 과제는 최근 게임 산업의 핵심 화두인 생성형 ai와 게임의 융합을 직접 프로젝트로 구현하며, 차세대 게임 개발 트랜드를 익히는 프로젝트이다.

1.3. 과제 진행 과정 및 내용 상세
1주차: 프로젝트 기획 구체화 및 시스템 아키텍처 설계
-동적 주도권 전이 메커니즘 설계
LLM을 활용하여 플레이어 캐릭터의 이중인격 페르소나를 구축하고, 특정 트리거 발생 시 제어권이 시스템(AI)으로 강제 이양되는 비대칭적 게임 루프를 기획했다.
대화의 품질과 협상 결과에 따라 캐릭터의 제어권이 복구되거나, AI가 임의로 적진에 돌진하는 등의 행동 페널티를 부여하여 심리적 긴장감을 유도하는 메커니즘을 정의했다.
-서사 기반 가변적 보스 시스템 고도화
고정된 스토리라인에서 탈피하여, NPC와의 상호작용 및 호감도 수치에 따라 해당 NPC가 최후의 적 또는 조력자로 분기되는 관계형 시나리오 알고리즘을 설계했다.
AI NPC의 의사결정 프로세스에 플레이어와의 누적 대화 데이터를 반영하여 매 플레이마다 고유한 서사적 경험을 제공하도록 기획했다.
이에 따라 AI NPC는 단순한 챗봇이 아닌, AI의 판단이 게임의 물리적인 수치에 직접적인 영향을 주게 만들어 AI가 게임을 직접 조절하여 플레이어에게 새로운 느낌을 주는 형태의 게임 메커니즘을 기획했다.
2주차 : 게임의 컨셉에 맞는 무료 2D 에셋(캐릭터,환경) 선정 또는 Nano Banana기반 에셋 생성
디자인이 가능한 팀원이 존재하지 않기에 무료 에셋이나 가격이 싼 에셋을 찾아보았고, 가능한 게임의 환경이 일관성 있도록 느껴지는 에셋을 찾아보았다.
‘대마왕의 침공으로 황폐화된 마을’이라는 서사적 배경을 시각적으로 구현하기 위해, 저채도와 어두운 톤 위주의 환경 에셋 가이드라인을 수립하였다.
글로벌 인디게임 리소스 플랫폼인 Itch.io를 활용하여 게임 컨셉에 부합하는 고품질 맵 타일셋(Tilemap)을 발굴하고 도입했다.
또한 월드에 몰입감을 주기 위해 NPC가 거주하는 집 또한 저채도 에셋을 찾아보고, 선정했다.

페르소나와 비주얼의 대조적 설계

이는 캐릭터가 겪는 삶의 풍파와 이중인격으로 인한 고난을 시각적으로 극대화하며, 유저로 하여금 캐릭터에 대한 연민과 몰입을 동시에 느끼게 하는 서사적 장치로 활용된다.
이중인격을 표현할 때에는 캐릭터 에셋의 눈 색깔을 빨간색으로 바꾸고, 화면에 글리치 효과를 넣어서 플레이어가 이중인격 AI가 나타났다는 걸 느낄 수 있게 만들기로 계획하였다.

본 단계에서는 2D RPG의 핵심 요소인 플레이어 캐릭터의 정교한 조작감을 확보하기 위해 캐릭터 컨트롤러 구현을 진행하였다. 특히 Unity 엔진에서 제공하는 다양한 입력 방식과 물리 제어 메커니즘을 심도 있게 분통해 본 프로젝트의 물리 환경에 최적화된 이동 로직을 도출하고 실제 개발 과정에 적용한 경과는 석하여, 프로젝트의 최적화와 확장성에 가장 부합하는 시스템을 구축하고자 하였다.
단순한 기능 구현을 넘어, 기존의 Input Manager와 최신 Input System의 구조적 차이를 검토하고, Transform 제어와 Rigidbody2D 물리 연산이 캐릭터 이동의 퍼포먼스와 안정성에 미치는 영향을 비교 분석하였다. 이를 다음과 같다.
Input Manager과 Input System 비교
2D 탑뷰 RPG는 이동, 상호작용, 스킬 사용 등 다양한 입력이 필요하며, 향후 패드 지원이나 키 변경 기능을 고려한다면 Input System 방식이 훨씬 효율적이고 확장성이 높다. 유니티 공식 문서의 Input Manager 항목에서도 Input Manager를 이전 기술(유산)으로 분류하고, 새 프로젝트에는 Input System 사용을 권장하고 있다.
2D 탑뷰 RPG에서 Input System이 유리한 이유
-다양한 상태 관리: RPG에는 '필드 이동', '전투', '인벤토리 창' 등 상태에 따라 입력값이 달라져야 하는데, Input System의 Action Maps를 사용하면 상태별로 입력을 통째로 껐다 켰다(Enable/Disable) 할 수 있어 로직이 훨씬 깔끔해진다.
-이동 입력의 일관성: 탑뷰 이동 시 키보드(WASD)와 조이스틱의 Vector2 값을 별도의 예외 처리 없이 동일한 로직으로 처리할 수 있다.
-이벤트 기반 최적화:Update 함수에서 매 프레임 키가 눌렸는지 검사(Polling)하는 대신, 입력이 발생했을 때만 함수를 호출하는 C# 이벤트 방식을 사용할 수 있어 성능과 코드 가독성 면에서 유리하다.
또한 유니티 공식 매뉴얼에서도 다음과 같이 명시하고 있다.
"Important: Input Manager is a legacy feature and not recommended for new projects. For new projects you should use the Input System Package.”
(중요: Input Manager는 레거시 기능이며 새 프로젝트에는 권장되지 않습니다. 새 프로젝트에는 Input System 패키지를 사용해야 합니다.)
Rigidbody2D기반 VS Transform.Position기반 움직임 비교
2D 탑뷰 RPG에서는 캐릭터가 벽이나 장애물에 충돌하고 밀어내는 등의 물리적인 상호작용이 필요하기 때문에 Rigidbody2D를 사용하여 물리 기반 이동 코드를 작성하였다. transform.position 코드는 단순히 좌표만 옮기는 방식이며 물리 연산을 무시하기 때문에 벽을 뚫는 현상이 잦은 반면, Rigidbody2D 기반 방식은 물리적인 상호작용이 훨씬 자연스럽고 버그가 적다.
漠杳Input System과 Rigidbody2D를 사용한 플레이어 이동 코드
벽 뚫기(Phasing) 방지 : `transform.position`을 사용하면 캐릭터의 좌표를 강제로 설정하기 때문에, 캐릭터가 벽 안으로 겹쳐질 수 있다. 이를 방지하려면 `Raycast` 등을 이용해 충돌 여부를 직접 코드로 검사해야 하는데, 이는 매우 복잡하고 불안정하다. 반면 `Rigidbody2D`는 물리 엔진이 스스로 계산하여 캐릭터가 벽을 뚫지 못하게 막아준다.
부드러운 미끄러짐 : 탑뷰 RPG에서 대각선 방향으로 벽에 비스듬히 걸어갈 때, 물리 기반 방식은 벽을 타고 부드럽게 미끄러지듯 이동한다. 이는 플레이어에게 훨씬 쾌적한 조작감을 제공한다.
유니티 내 Rigidbody2D 공식 문서에서도 물리적인 상호작용에는 Rigidbody2D를 사용하라고 되어있다.
"Note: You can override the Rigidbody 2D by directly modifying the Transform component yourself... However, this will cause issues such as unpredictable movement or GameObjects passing through and into each other."
(참고: Transform 컴포넌트를 직접 수정하여 Rigidbody 2D를 덮어쓸 수 있습니다... 하지만 이는 예측할 수 없는 움직임이나 게임 오브젝트가 서로 통과해버리는 등의 문제를 일으킬 수 있습니다.)
"Moving the Rigidbody 2D provides the best performance and ensures correct collision detection."
(Rigidbody 2D를 움직이는 것이 최상의 성능을 제공하고 정확한 충돌 감지를 보장합니다.)

8주차 : 로컬LLM 구동을 위한 Ollama 설치 및 경량화 모델(Llama-3-8B) 적용
로컬 LLM(Local LLM) 도입 배경
-보안 및 독립성: 외부 API(OpenAI 등)를 사용하지 않고 로컬 환경에서 모델을 구동함으로써, 인터넷 연결 없이도 동작 가능한 독립적인 게임 환경을 구축하였다.
-비용 효율성: 지속적인 API 호출 비용 발생 문제를 해결하기 위해, 사용자 기기의 자원을 활용하는 로컬 구동 방식을 채택하였다.
방대한 자료 및 커뮤니티 생태계: 글로벌 커뮤니티에 공개된 수많은 양자화 모델과 최적화 라이브러리, 풍부한 구현 사례를 바탕으로 학생 수준에서도 고성능 AI 시스템을 안정적으로 구축할 수 있는 환경을 활용할 수 있다.
Ollama 설치 및 인프라 구성
-프레임워크 선정: 다양한 LLM을 간편하게 관리하고 서빙할 수 있는 오픈소스 도구인 Ollama를 설치하였다.
-유니티 연동(LLMUnity): Ollama 서버와 유니티 엔진 간의 통신을 위해 LLMUnity 패키지를 도입하였으며, 이를 통해 스크립트 기반의 비동기 채팅 시스템을 완성하였다.
-모델 선정: Meta에서 공개한 오픈소스 모델인 Llama-3-8B를 채택하였으며, 해당 모델은 80억 개의 파라미터를 가지고 있어 한국어 이해 능력이 뛰어나고 NPC 대화에 적합한 성능을 가지고 있다고 판단해 선정하게 되었다.
