## 2. 배열: ID로 바로 접근하는 상태 저장

주요 배열은 다음과 같다.

- `RpgSkillCatalog.All`: 스킬 정의 9개.
- `AttributeRanks`: 체력·공격·방어·내공 투자량 4개.
- `SkillRanks`: 스킬별 학습 랭크 9개.
- `readyAt`: 스킬별 재사용 가능 시각 9개.
- `Hotbar`: 단축키에 배치할 스킬 ID `{ 0, 3, 6 }`.

배열의 인덱스가 곧 ID다. `SkillRanks[3]`은 금강호신의 랭크이고 `readyAt[3]`은 같은 스킬의 다음 사용 가능 시각이다. 별도 이름 검색 없이 인덱스로 접근하므로 개별 조회는 O(1)이다. 스킬 수를 S, 능력치 수를 A라고 하면 상태 배열 공간은 O(S+A)다.

현재처럼 작고 고정된 목록에는 간단하고 효율적이다. 다만 배열 순서를 바꾸면 저장된 랭크가 다른 스킬에 연결될 수 있다. 스킬을 대량 추가할 때에는 안정적인 문자열 ID와 저장 버전 변환을 도입하는 편이 안전하다. 이는 개선안이며 현재 구현은 숫자 인덱스 기반이다.

`readonly` 배열 필드는 배열 자체의 재할당을 막지만 원소 교체까지 막지는 않는다. 또한 공개된 랭크 배열을 외부 코드가 직접 수정하면 검증 메서드를 우회할 수 있다.

## 3. 스킬트리: 부모 인덱스로 표현한 의존 관계

현재 스킬 관계는 독립된 세 개의 선형 체인이다.

```text
검술: 0 월영참   → 1 검의 이치 → 2 검성의 경지
호신: 3 금강호신 → 4 철골      → 5 불굴
내공: 6 운기조식 → 7 기맥 순환 → 8 삼화취정
```

자료구조 관점에서는 여러 트리로 이루어진 포리스트이며, 이진 탐색 트리는 아니다. 각 정의의 `Prerequisite`가 직전 부모 ID를 저장한다. 첫 스킬은 -1로 부모가 없음을 나타낸다.

`SkillLockReason(id)`는 ID 유효성, 최대 랭크, 요구 레벨, 선행 스킬 학습 여부, 남은 스킬 포인트를 차례로 검사한다. 실패한 첫 이유를 문자열로 반환하고, 빈 문자열이면 학습할 수 있다.

선행 스킬은 바로 앞 노드의 랭크가 1 이상인지 확인한다. 정상적인 학습 경로에서는 앞 노드도 같은 검증을 거쳤으므로 전체 조상을 DFS/BFS로 탐색할 필요가 없다. 검사 자체는 O(1)이다. 그러나 외부에서 수정한 저장 파일의 의존 관계까지 이 검사만으로 완전히 보장하지는 않는다.

현재는 다중 선행 조건, 순환 참조 검사, 자동 그래프 배치가 없다. UI 역시 `column * 3 + tier`로 고정 3열·3단을 배치하므로 데이터만 늘린다고 화면이 자동 확장되지는 않는다.

## 4. 포인트 투자: 검증 후 상태 변경

`UpgradeAttribute`는 잘못된 ID나 포인트 부족을 먼저 거부한 다음 포인트를 하나 차감하고 해당 투자량을 올린다.

- 체력: 최대 HP +20, 살아 있다면 현재 HP도 +20.
- 공격: 투자당 공격 보너스 +2.
- 방어: 투자당 방어력 +2.
- 내공: 최대 MP와 현재 MP +10.

패시브까지 포함한 계산식은 다음과 같다.

```text
공격 보너스 = 공격 투자량×2 + 검의 이치 랭크×3 + 검성의 경지 랭크×6
방어력 = 방어 투자량×2 + 철골 랭크×3 + 불굴 랭크×6
초당 MP 회복 = 1 + 기맥 순환 랭크×0.6 + 삼화취정 랭크×1.2
```

고정 개수의 값만 읽으므로 수치 계산은 O(1)이다. 단, 투자 메서드는 저장까지 호출하므로 전체 비용을 O(1)이라고만 표현하면 파일 입출력 비용을 빠뜨린다.

## 5. 스킬 사용: 실패 조건을 먼저 걸러내는 알고리즘

`TryCast`는 유효한 액티브 스킬인지, 플레이어가 행동 가능한지, 학습했는지, 쿨다운이 끝났는지 등을 확인한다. 공격 스킬은 공격 컴포넌트와 대시 상태를 확인하고, 회복 스킬은 실제로 잃은 HP가 있는지 확인한다. 이후 MP를 소비하고 재사용 시각을 기록한 뒤 효과를 실행한다.

이 순서 덕분에 HP가 가득 찬 상태의 회복 시도나 쿨다운 중 입력은 MP를 낭비하지 않는다. 다만 효과 실행 중 예외가 발생했을 때 이미 소비한 MP를 되돌리는 전체 트랜잭션 시스템은 아니다.

UI 열림, 대화, 일시정지, 사망, 조작권 상태도 검사한다. UI를 여는 것은 게임 전체 일시정지가 아니라 플레이어 입력을 막는 동작이라는 점이 중요하다.

## 6. 쿨다운: 남은 시간을 계속 감소시키지 않는다

```text
사용 시: readyAt[id] = Time.time + Cooldown
조회 시: remaining = max(0, readyAt[id] - Time.time)
```

예를 들어 시각 20초에 5초짜리 스킬을 사용하면 readyAt은 25가 된다. 시각 22초에는 남은 시간이 3초다. 각 스킬을 매 프레임 순회하며 타이머를 감소시키지 않아도 되며 개별 조회는 O(1)이다.

Time.time은 게임 시간 배율의 영향을 받는다. 반면 UI의 주기적 갱신은 unscaledTime을 사용한다. 따라서 일시정지 중 화면 갱신은 가능하지만 스킬 쿨다운은 진행하지 않는다. 쿨다운과 호신 지속 시간은 저장 데이터에 없으므로 재실행하면 초기화된다.

## 7. HashSet: 콜라이더가 여러 개여도 한 번만 피해

몬스터 하나에 몸통·머리 등 여러 Collider2D가 있을 수 있다. 충돌 검색 결과를 그대로 순회하면서 매번 피해를 주면 한 공격으로 같은 몬스터를 여러 번 때리는 문제가 생긴다.

월영참은 `HashSet<MonsterBase>`, 일반·대시 공격은 `HashSet<IDamageable>`로 이미 처리한 대상을 기억한다. 개념적으로 다음과 같다.

```csharp
foreach (var collider in hits)
{
    var target = collider.GetComponentInParent<MonsterBase>();
    if (target != null && damaged.Add(target))
        target.TakeDamage(damage);
}
```

`Add`는 처음 들어오는 대상일 때만 true다. 집합은 공격 한 번마다 새로 만들어지므로 다음 공격에서는 같은 적을 다시 때릴 수 있다. 중복 제거 기준은 콜라이더가 아니라 피해 수신 컴포넌트다.

H를 검색된 콜라이더 수, U를 서로 다른 대상 수, D를 부모 계층 탐색 깊이라고 하자. HashSet 추가의 평균 비용은 O(1)이므로 처리 루프는 기대 O(H×D), 집합 공간은 O(U)다. 검색 결과 배열에는 O(H) 공간이 필요하다. 여기에 물리 엔진 검색 비용이 따로 더해진다. 전체 충돌 검색까지 무조건 O(H)라고 단정할 수는 없다.

## 8. 전투 수식과 공격 범위

월영참 피해는 다음과 같다.

```text
최종 공격력 = 기본 공격력 + 공격 보너스
월영참 피해 = Round(최종 공격력 × (1.8 + (월영참 랭크-1)×0.4))
월영참 반경 = 2 + 검성의 경지 랭크×0.4
검색 중심 = 플레이어 위치 + 공격 방향×반경×0.6
```

최종 공격력 10, 월영참 1랭크라면 피해는 18이다. 판정은 전방으로 중심을 옮긴 원형 검색이다. 정확한 부채꼴이 아니며 플레이어 뒤쪽 일부도 원 안에 들어갈 수 있다.

플레이어가 받는 피해는 다음과 같다.

```text
실제 피해 = max(1, Round(입력 피해 × 100/(100+방어력×4) × 호신 배율))
호신 배율 = 호신 활성 시 0.65 - 금강호신 랭크×0.08, 아니면 1
```

입력 피해 100, 방어력 25라면 호신 없이 50이다. 금강호신 1랭크의 배율은 0.57이고 지속 시간은 6초다. 방어력과 호신은 곱으로 적용되며, 최소 피해는 1로 제한된다.

운기조식은 최대 HP의 `0.2 + (운기조식 랭크-1)×0.08 + 삼화취정 랭크×0.05`만큼 회복한다. 최종 HP는 최대 HP를 넘지 않으며 사망한 플레이어를 부활시키지는 않는다.

## 9. 경험치: while로 한 번에 여러 레벨 처리

AddEXP는 경험치를 더하고 현재 레벨 요구량 이상인 동안 요구량을 빼고 LevelUp을 반복한다. if 한 번만 사용하면 많은 경험치를 획득했을 때 연속 레벨업을 처리하지 못한다.

레벨업마다 스탯 포인트 +3, 스킬 포인트 +1, 최대 HP +20, 최대 MP +10이 적용된다. 다음 요구 경험치는 현재 요구량에 1.5를 곱하고 반올림한다.

초기 레벨 1, 경험치 0, 요구량 100에서 250을 얻으면 100을 써서 레벨 2, 다시 150을 써서 레벨 3이 된다. 남은 경험치는 0, 다음 요구량은 225다. 아무 포인트도 사용하지 않았다면 초기 5/3포인트에서 스탯 11, 스킬 5포인트가 된다.

이번에 오른 레벨 수를 L이라고 하면 성장 계산은 O(L)이다. 하지만 현재는 LevelUp마다 저장하고 AddEXP 마지막에도 저장한다. 저장 크기를 B라고 하면 입출력을 포함한 비용은 대략 O((L+1)×B)다. 여러 레벨을 처리한 뒤 한 번만 저장하는 개선 여지가 있다.

## 10. UI: 참조 캐시와 주기 갱신

UI는 uGUI와 TextMeshPro를 코드로 생성한다. 스킬 노드 9개, 능력치 값·버튼 4개, 단축키 표시 3개를 배열에 보관한다. 갱신할 때마다 하위 오브젝트를 이름으로 검색하지 않고 저장한 참조에 직접 접근한다.

정기 Refresh는 unscaledTime 기준 약 0.1초 간격이다. 레벨업 이벤트와 버튼 동작 등에 따른 즉시 갱신도 있으므로 모든 갱신을 합쳐 정확히 초당 10회로 제한한 것은 아니다. OnStatsChanged를 전부 구독하는 방식이 아니라 폴링과 일부 이벤트를 섞은 구조다.

닫힌 상태에서는 HUD와 단축키를 갱신하고 상세 패널 처리는 건너뛴다. 열린 상태의 논리적 순회 비용은 O(S+A+K)이며 K는 단축키 개수다. 텍스트 메시 재생성과 Canvas 재빌드 비용은 이 반복문 비용과 별개다.

HP/MP 바는 Image.fillAmount가 아니라 RectTransform.anchorMax.x에 0~1 비율을 넣어서 너비를 조절한다. 버튼 이벤트의 람다는 반복문 안의 개별 id/slot 변수를 캡처해 해당 스킬에 연결된다.

## 11. 절차적 문양과 이펙트의 기하 알고리즘

RpgSkillEmblem은 MaskableGraphic을 상속하고 OnPopulateMesh에서 선분을 사각형으로 만든다. 양 끝점 a, b와 두께 w에 대해 방향 d=b-a의 수직 단위 벡터에 w/2를 곱한 n을 구하면 사각형 꼭짓점은 a+n, a-n, b+n, b-n으로 구성할 수 있다.

선분 하나당 정점 4개와 삼각형 2개가 필요하다. 선분 수를 E라고 하면 생성 비용과 메시 크기는 O(E)다. 현재는 계열별 문양을 반복 사용해 저비용으로 구분하지만, 스킬별 개성이 약해지는 한계가 있다.

스킬의 원형 효과는 48개 점을 sin/cos로 계산하고 약 0.45초 동안 크기와 투명도를 바꾼다. 프레임당 계산량은 점 개수 V에 대해 O(V)다. 코루틴은 별도 작업 스레드가 아니며 deltaTime 기반이므로 게임 시간 정지의 영향을 받는다. 반복적인 오브젝트·재질 생성은 향후 풀링 대상으로 볼 수 있다.

## 12. 저장: DTO, 직렬화, 임시 파일과 백업

PlayerSaveData는 동작보다 저장할 값에 집중한 DTO다. 레벨, HP/MP/EXP, 최대값, 포인트, 랭크 배열, progressionVersion을 JSON으로 직렬화한다.

저장은 player_save.json.tmp에 먼저 기록한다. 기존 본파일이 있으면 File.Replace로 교체하면서 .bak 백업을 남기고, 없으면 임시 파일을 본파일로 이동한다. 기존 파일을 직접 조금씩 덮어쓰는 위험을 줄이는 방식이지만 모든 환경에서 무손실을 보장하는 것은 아니다. 저장 실패 시 로그를 남길 뿐 게임 상태를 되돌리지 않는다.

로드는 주 파일을 읽고 기본적인 유효성을 확인한다. 읽기·파싱·검증에서 예외가 나면 백업을 시도한다. 주 파일이 아예 없으면 현재 코드는 바로 null을 반환하므로 백업만 남아 있는 상황은 자동 복구하지 않는다.

유효성 검사는 레벨 범위, 최대값의 양수 여부, NaN/Infinity 등을 확인하고 PlayerStats.Load에서 랭크와 포인트 등을 보정한다. 모든 악의적인 저장 조작을 막는 보안 시스템은 아니다.

옛 progressionVersion 0 데이터에는 레벨 기반 기본 포인트를 부여한다. 이후 버전 1로 저장하므로 매번 접속할 때 포인트를 다시 지급하지 않는다. 최대 HP/MP는 이미 저장된 값을 복원하므로 투자량을 다시 더해 중복 적용하지 않는다.

파일 크기를 B라고 하면 직렬화·읽기·쓰기 비용은 대략 O(B)다. 현재 동기식 입출력이므로 메인 스레드에서 실행되며, 백업도 읽어야 하면 그 비용이 추가된다.

## 13. 퀘스트 시스템에서 쓰는 다른 자료구조

[QuestManager.cs](../Assets/Script/Quest/QuestManager.cs)는 `Dictionary<string, QuestRuntime>`으로 퀘스트 ID와 실행 상태를 연결한다. 평균적인 해시 조회는 O(1)이지만 문자열 해시 계산 비용은 ID 길이의 영향을 받는다.

[QuestData.cs](../Assets/Script/Quest/QuestData.cs)의 정의 데이터와 실행 중 진행도 배열·상태를 분리한다. 공유 ScriptableObject 원본을 플레이어 진행 상황으로 직접 덮어쓰지 않는 구조다.

Report는 전체 퀘스트에서 진행 중인 항목의 스냅샷을 만들고 목표를 순회한다. 퀘스트 수를 Q, 활성 목표 수 합을 M이라고 하면 기본 검색·진행도 처리는 O(Q+M)이다. 완료 이벤트, 후속 해금, 저장의 연쇄 실행은 추가 비용이다. 스냅샷은 이벤트 도중 상태가 바뀌는 상황에서 순회를 안정적으로 진행하는 데 도움이 된다.

해금과 완료가 연쇄 호출될 수 있지만 일반적인 위상 정렬이나 BFS 알고리즘으로 구현되어 있지는 않다. 또한 퀘스트 저장과 플레이어 저장은 별개여서 둘을 하나로 묶는 원자적 저장 트랜잭션은 없다.

## 14. 검증 근거와 구현되지 않은 기능

기존 검증 스크립트는 [RpgVerification.cs](../Assets/Script/Editor/RpgVerification.cs), [RpgPlayVerification.cs](../Assets/Script/Editor/RpgPlayVerification.cs)에 있다. 문서 작성 중 확인한 기존 결과 파일은 각각 `PASS: 23 assertions`, `PASS: 13 play-mode combat assertions`였다. 이번 문서 작성 작업에서 Unity 테스트를 새로 실행한 것은 아니다.

검증 범위에는 스탯 투자, 잘못된 ID, 포인트 부족, 성장, 저장 복원, 구버전 변환, 백업 복원, UI 생성, 회복·MP·쿨다운·호신, 복수 콜라이더 중복 피해 방지가 포함된다. 이것이 모든 장면과 모든 해상도에 대한 완전한 검증을 의미하지는 않는다.

현재 RPG 성장 UI에 장비 인벤토리, 스탯 초기화, 사망 후 부활, 일반적인 다중 부모 스킬 그래프 편집기가 구현된 것은 아니다. 외형 개선 시에는 전투·저장 규칙을 유지하고 UI의 프레임·아이콘·배치 계층을 교체하는 편이 변경 범위를 줄인다.

## 15. 핵심 요약

배열로 작은 고정 목록을 빠르게 조회하고, 부모 인덱스로 스킬 의존 관계를 표현한다. HashSet은 공격 한 번의 중복 피해를 제거한다. 쿨다운은 종료 시각과 현재 시각의 차이로 계산하고, while은 연속 레벨업을 처리한다. UI는 참조 캐시와 주기 갱신을 사용하며, 저장은 DTO를 JSON으로 직렬화해 임시 파일·백업과 함께 관리한다.

계산 자체가 O(1)인 기능도 실제 실행 비용에는 물리 검색, UI 재빌드, 문자열 생성, 파일 입출력이 더해진다는 점이 이 코드의 성능을 설명할 때 가장 중요하다.
