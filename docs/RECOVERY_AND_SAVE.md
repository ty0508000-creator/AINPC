# 사망 복구와 통합 저장

2026-09-20 · 개발 계획 P0-1 / P0-6 후속 구현.

## 플레이어에게 보이는 변화

HP가 0이 되면 목재/종이 재도전 화면이 나타난다. 버튼 또는 R로 마지막 체크포인트에 돌아가고 HP/MP를 전부 회복한다. 성장·경험치·무공·퀘스트·Mood는 잃지 않는다. 사망 중 레벨업해도 부활하지 않으며, 종료 후 다시 시작해도 재도전 화면에서 복구할 수 있다.

재도전은 살아 있을 때 호출할 수 없다. 사망 시 AI 이동과 공격/대시 코루틴을 중단하고, 사망한 캐릭터의 강제 공격 API도 차단한다. 복귀 시 조작권을 플레이어에게 돌려주고 무공 쿨타임/호신 효과를 초기화한다. 피해를 막는 2초 보호 시간은 게임 시간 기준이다.

NPC 대화는 사망 시 닫고, 활성 내면 대화는 자신의 정지 시간과 화면을 복원한다. 일반적인 LLM 요청 취소/오래된 응답 격리는 P0-2/3의 별도 작업이며 이번 변경으로 해결됐다고 간주하지 않는다.

## 체크포인트 배치

체크포인트가 없으면 플레이어가 씬에 생성된 위치를 사용한다. 자동으로 안전한 지형을 찾는 기능은 아니다.

1. 안전한 위치에 빈 GameObject와 Collider2D를 만든다.
2. Collider2D의 Is Trigger를 켜고 `PlayerCheckpoint`를 추가한다.
3. 필요하면 별도의 Transform을 `Respawn Point`에 연결한다. 없으면 체크포인트 오브젝트 위치로 복귀한다.
4. 플레이어 콜라이더가 들어오면 `PlayerStats.SetCheckpoint`가 좌표와 씬 경로를 저장한다.

다른 씬의 좌표는 현재 씬에 적용하지 않고 현재 씬 시작 위치를 사용한다. 이번에는 사용자가 열어 둔 씬이나 프리팹을 변경하지 않았으므로, 원하는 마을/보스 앞 안전 지점은 후속 배치해야 한다.

적 초기화 정책: 살아 있는 적의 현재 상태는 유지하고, 처치한 보스를 복귀 코드가 재생성하지 않는다. 월드 전체 영속 저장/체크포인트별 적 리셋은 이번 범위가 아니다. 새 씬 로드시 원래 스폰 시스템의 동작은 유지된다.

## 저장 형식과 순서

파일명은 기존 `player_save.json`을 유지한다. `snapshotVersion=3`에는 성장·퀘스트·체크포인트·Mood·인벤토리와 현재 씬/좌표/진행 표시를 함께 넣는다. 기존 `progressionVersion`과 스킬 배열 인덱스는 바꾸지 않았다.

저장 순서는 전체 데이터 캡처 → 같은 폴더의 `.tmp` 작성 → 파일 flush → 내용 재검증 → 원자적 파일 교체다. 이전 정상 저장은 `.bak`으로 남긴다. 손상된 주 파일을 수리할 때는 정상 백업을 손상 데이터로 덮지 않는다. `.tmp`는 커밋되지 않은 데이터로 간주하여 로드하지 않는다.

퀘스트 완료/실패/거절은 한 경로로 처리한다. 종료 상태, EXP에 따른 모든 레벨업, Mood 변화, 직접 해금 상태를 먼저 반영하고 **중간 저장이나 이벤트 없이** 하나의 파일에 기록한다. 이후 UI 알림·조작권 평가·기억 기록·연출을 수행한다.

퀘스트 ID의 Completed/Failed가 영속적인 수령 표식이다. 반복 가능한 퀘스트가 없는 현재 구조에서는 별도 claimId보다 이 표식과 보상을 같은 파일에 넣는 것으로 중복 호출을 방지할 수 있다. 반복 퀘스트를 추가하면 회차별 claimId가 필요하다.

커밋 후 연출 전에 종료되더라도 보상과 종료 상태는 함께 남는다. 해금된 autoStart 퀘스트는 다음 로드에서 이어 시작한다. 목표를 다 채운 Active 상태도 시작 시 완료를 재평가한다.

## 마이그레이션과 복구

- 예전 플레이어 파일과 `quest_save.json`은 첫 통합 저장에서 함께 가져온다. 예전 퀘스트 파일을 삭제하거나 덮지 않는다.
- 이미 통합된 저장이 있으면 오래된 분리 퀘스트 파일은 무시한다.
- 주 파일이 없거나 손상되면 백업의 플레이어/퀘스트를 함께 읽는다. 서로 다른 파일 버전을 섞어 복구하지 않는다.
- 두 저장본이 모두 손상되면 저장을 거부하여 원본을 보존한다. 실행 중 새 기본 상태가 보이더라도 기존 파일을 덮지는 않는다.
- 더 최신 snapshotVersion도 자동으로 구형 백업에 덮어쓰지 않는다.
- 저장 실패 시 메모리의 현재 진행은 유지하고 경고를 보여준다. 뒤의 저장 시도는 재시도하지만, 성공 전 종료하면 마지막 정상 저장 시점으로 돌아간다.
- `DeleteSave` API는 통합 일관성을 위해 플레이어/퀘스트/백업/임시 파일 전체 슬롯 초기화 의미로 통일했다. 이번 작업에서 실제 사용자 슬롯에 이 API를 실행하지 않았다.

구버전 파일이 이미 서로 어긋난 경우 어느 보상을 받았는지 증거가 없으므로 자동 재구성할 수 없다. 기존 파일을 보존하는 이유다. 이 경우 수동 판단이 필요하다.

## 검증 재실행

Unity는 작업 씬을 저장하고 종료하거나, 별도 프로젝트 복사본에서 실행한다. 검증은 빈 씬을 생성한다. 실제 사용자 저장 대신 GUID 이름의 전용 폴더를 사용한다.

```powershell
& 'C:/Program Files/Unity/Hub/Editor/6000.3.10f1/Editor/Unity.exe' -batchmode -projectPath C:/AINPC -executeMethod RecoverySaveVerification.Run -quit -logFile C:/AINPC/Temp/recovery-save.log
```

추가로 `RpgVerification.Run`과 `RpgPlayVerification.Run`을 실행한다. Play 검증은 스스로 종료하므로 `-quit`을 붙이지 않는다. PowerShell이 먼저 돌아와도 테스트 완료가 아니며 로그의 PASS와 `VerificationResults`의 결과 파일을 확인한다.

검증 내용: 반복 피해 단일 사망 이벤트, 사망 중 성장/마나 제한, 사후 레벨업, 재실행 복구, 체크포인트, 성장 유지, 보호 시간, AI 조작 사망과 강제 공격 차단, UI 버튼, 통합 보상, 실패/거절 재지급 방지, 다중 레벨업, 커밋 전 오류, 커밋 후 재로드, 백업 없음/손상/복원, legacy migration, 다음 자동 퀘스트 복구, 미래 형식 보호.

중단 검사는 커밋 직전 예외를 주입하고 디스크를 다시 읽는 방식이다. 실제 전원 차단이나 모든 파일시스템의 내구성을 검증한 것은 아니다. RAG 기억 쓰기·LLM 응답·연출은 파일 트랜잭션 밖이며 exactly-once 보장 범위가 아니다. 실제 Main 완주/마우스 입력/배포 빌드/체크포인트 지형도 별도 확인이 필요하다.
